# Phase K45 · Mobile white-screen regression on Schedule with assigned jobs — SHIPPED

**Feb-2026 · P0 hotfix · Mobile only · No web / backend / K43 / K41d touched**

---

## Root cause

`@/src/lib/maps/hereAdapter.tsx` (added in K39b) called
`require("react-native-here-explore")` at **module scope**. Even though it was
wrapped in try/catch, the try/catch only guarded the *JS module resolution* —
if the package resolved but its native constructor threw at import time
(exactly the case when the `.aar` / `.xcframework` binaries are missing from
`mobile/heresdk/`), the whole shell crashed before any React error boundary
could mount.

Metro/EAS made this worse because `@/src/lib/maps/index.ts` did
`import * as _here from "./hereAdapter"` at the top level, so the eager
`require` fired unconditionally, regardless of `EXPO_PUBLIC_MAPS_PROVIDER`.
On a Schedule tab with assigned jobs, that meant a silent white screen.

## Fix (six workstreams)

| # | File | Change |
|---|---|---|
| 1 | `mobile/src/lib/maps/hereAdapter.tsx` | `require("react-native-here-explore")` moved out of module scope into a lazy `_loadHere()` helper. Every export calls the helper from inside its function body and short-circuits to the placeholder on any failure. Memoized in module scope so the require fires at most once per session. |
| 2 | `mobile/src/lib/maps/index.ts` | Dropped the static `import * as _here from "./hereAdapter"`. The HERE adapter is now `require()`'d only inside a runtime gate that fires only when `_computeProvider() === "here"`, with a silent try/catch downgrade to the Google adapter. |
| 3 | `mobile/src/lib/maps/provider.ts` | New runtime gate that consults the generated `HERE_BINARIES_PRESENT` constant and downgrades `here → google` (with a one-shot warning) if the native binaries are absent — even when the env flag + access key are set. |
| 4 | `mobile/scripts/heresdk-check.js` | Postinstall hook now (a) writes a `mobile/heresdk/.MISSING` marker file when binaries are absent (deleted when present) and (b) regenerates `mobile/src/lib/maps/heresdkStatus.generated.ts` with the current `HERE_BINARIES_PRESENT` boolean, so the runtime gate operates from a bundled constant with zero fs access. |
| 5 | `mobile/src/lib/maps/heresdkStatus.generated.ts` | New generated file. Default `false` (safe). Regenerated by the postinstall hook on every `yarn install`. |
| 6 | `mobile/__tests__/k45-lazy-here.test.ts` | New regression suite (5 tests) covering: (a) no module-scope `require` in `hereAdapter.tsx`, (b) no static `import` of `./hereAdapter` in `index.ts`, (c) `here → google` downgrade on missing binaries, (d) `here` resolves normally when binaries present, (e) barrel import in google mode does NOT touch `react-native-here-explore`. |

## Non-goals (per brief)

- **No HERE binaries** shipped into the repo.
- **No changes** to K43 (ACH bank verification) or K41d (bulk-op audit tile) code paths.
- **No web** changes.
- **No changes** to what the Schedule tab renders — Google adapter continues to render exactly as before; only the boot path is safer.
- `RootErrorBoundary` was already wired at `mobile/app/_layout.tsx:132` (K36 · P2→P0 hotfix companion). No changes needed — the boundary was correct all along; the crash happened *before* it could mount because `require` fired at module resolution time. K45 fixes the root cause by removing the eager require.
- `mobile/__tests__/maps-abstraction.test.ts` "flag=here + key present" case was updated to also mock `HERE_BINARIES_PRESENT=true` — this is a correct behavior change (the resolver now gates on binaries too), not a workaround.
- K42 null-guards on `assigned_tech_id` / `assignee` in Schedule — verified as no-op: no unsafe dereferences of those fields exist in `mobile/app/(app)/schedule/**` or `mobile/src/components/schedule/**`. Only `technician_id` is referenced, always with `user?.id`.

## EAS rebuild call-out

Because the K45 fix touches JS-only files, **no native rebuild is required**
for the fix itself. However:

- Devices already installed with the crashing build must pull a JS bundle
  update (OTA via `expo publish` / EAS Update) before they'll see the fix.
- On the next full EAS build (whenever it happens for another reason), the
  postinstall hook will run and regenerate `heresdkStatus.generated.ts`
  from the current binary state — no manual action needed.
- If we ever drop the HERE `.aar` / `.xcframework` into `mobile/heresdk/`,
  the same postinstall will flip `HERE_BINARIES_PRESENT` to `true` and delete
  the `.MISSING` marker, at which point `EXPO_PUBLIC_MAPS_PROVIDER=here`
  will start routing traffic to HERE again.
